## Why

A researcher running the packaged artifact cannot obtain a Globus credential at all. Minting one
is `scripts/get_globus_token.py`, and `scripts/` is not installed by the package, so the only path
from a fresh install to working file transfer runs through a source checkout. What the launcher
offers instead is an environment variable the researcher must export before `./vista` — the exact
friction the desktop package exists to remove.

The credential model is also the wrong shape here. `VISTA_MCP_ODO_GLOBUS_REFRESH_TOKEN` is a
deployment-wide secret: one shared Globus identity for every user of a server. On a laptop the
deployment and the user are the same person, and the token is simply configuration the
application should ask for, the way it already asks for an inference credential and an S3M token.

## What Changes

- A **Connect Globus** control in the user settings interface, one per OLCF cluster. It presents
  the Globus authorization address and a box for the single-use code that address returns, which
  is `scripts/get_globus_token.py`'s flow with the terminal replaced by the interface the
  researcher is already in.
- The resulting **Transfer refresh token is stored per user and encrypted at rest**, in
  per-cluster fields mirroring the existing `odo_s3m_token` / `frontier_s3m_token` pair. Odo and
  Frontier pin different SSO domains and can be different identities, so one field cannot serve
  both.
- **Credential resolution becomes per-user-when-present, deployment environment variable
  otherwise.** The hosted multi-user deployment keeps working exactly as it does today, and its
  shared-identity assumptions are unchanged for anyone who has not connected their own.
- **The local collection is created from a setup key rather than a terminal login.** With a
  Transfer token in hand the application creates the Globus Connect Personal endpoint through the
  Transfer API and hands the returned setup key to the existing non-interactive setup path. The
  terminal login remains as the fallback for a headless install.
- **The transfer endpoint starts on demand instead of at launch.** A credential that arrives from
  the interface cannot inform a decision the launcher made before any user signed in.
  **BREAKING** for the launcher's current behaviour: it no longer starts or holds the endpoint,
  and the startup line it prints about unavailable clusters is replaced by state the interface and
  the job tools report.

Out of scope, deliberately: NERSC IRI tokens, which are a different credential on a different
flow and already entered in the interface; any change to what Globus Connect Personal is allowed
to see; and HTTPS transport, which would remove the local endpoint entirely and is a separate
question.

## Capabilities

### New Capabilities

None. This change moves an existing capability from an environment variable to the interface.

### Modified Capabilities

- `zero-config-startup`: "Inference credentials supplied through the interface" establishes that a
  credential is accepted by the running application, stored encrypted, and effective without a
  restart. File-transfer credentials gain the same guarantee, plus what is particular to them —
  the credential is obtained through an authorization step the application guides rather than
  assumes the researcher can perform elsewhere. "Optional file-transfer setup never blocks
  startup" currently frames setup as something attempted at launch when credentials are already
  configured; the trigger moves to the interface, and the requirement has to stop naming launch as
  the moment it happens.
- `laptop-distribution`: "Job submission preserved" requires the artifact to carry what a local
  transfer endpoint needs. It does not require the artifact to carry a way to *obtain* the
  credential that endpoint's transfers authenticate with, which is why a packaged researcher can
  currently reach a working endpoint and still be unable to move a file.

## Impact

- `ui/components/UserSettingsModal.tsx`, `ui/lib/user.ts` — a Connect Globus control per cluster;
  unlike every other field in the modal, it is a two-step exchange rather than a value to save.
- `backend/src/vista_backend/` — two endpoints, one starting the authorization flow and one
  exchanging the code. The PKCE verifier generated by the first has to survive until the second,
  so the flow holds short-lived server-side state keyed to the user.
- `backend/src/vista_backend/db/schemas.py` — per-cluster token fields beside the existing
  `globus_token`. `_add_missing_columns` adds nullable columns at startup, so no migration.
- `mcp_servers/vista_mcp_server/src/vista_mcp_server/lib/user_config.py` — the fields the MCP
  server reads, and a `require_globus_token(cluster)` that prefers the user's over the
  deployment's, mirroring `require_s3m_token`.
- `mcp_servers/vista_mcp_server/src/vista_mcp_server/submit_job_mcp.py` — five call sites resolve
  the token through the user's configuration rather than settings alone.
- `mcp_servers/vista_mcp_server/src/vista_mcp_server/lib/gcp_vm.py` — creating the collection from
  a setup key, and an owner for the endpoint process now that the launcher is not one. `start`,
  `stop` and `status` are already callable at any time; what is missing is something holding the
  process for the session.
- `scripts/package_launcher.sh`, `scripts/launch.sh` — the refresh-token gate and the fourth
  managed service are removed.
- `globus_sdk` is already a dependency of `vista_mcp_server`; the backend gains it.
- `README.md` — the exported-variable instructions become the interface flow.
